# ClaimGPT: Backend Production Implementation Plan

This checklist outlines the concrete, step-by-step developer tasks required to transition the ClaimGPT backend from the local Docker-integrated state into a secure, scalable, and HIPAA-compliant Azure production environment for your 350-employee pilot.

---

## Task 1: Entra ID Authentication & Role-Based Access Control (RBAC)

### [ ] Step 1.1: Disable Local Auth Endpoints
* Locate `/auth/login`, `/auth/register`, `/organizations/registration`, and `/tpa-adjusters/registration` routes in [services/ingress/app/main.py](file:///c:/Project/ClaimGPT-feature/services/ingress/app/main.py).
* Guard or disable these routes for production environments, leaving them active only under a `dev` configuration switch.

### [ ] Step 1.2: Implement JWT Verification Middleware
* Implement a FastAPI Dependency `get_current_user` in `libs/auth/` that:
  1. Reads the `Authorization: Bearer <JWT>` header from incoming API requests.
  2. Fetches Microsoft's public OpenID Connect keys from `https://login.microsoftonline.com/{tenant_id}/discovery/v2.0/keys`.
  3. Uses a library like `python-jose` or `PyJWT` to verify the signature, expiration (`exp`), audience (`aud`), and issuer (`iss`) of the Entra ID access token.
  4. Extracts claims like the user's email (`preferred_username`), unique subject ID (`sub`), and security groups/roles.

### [ ] Step 1.3: Map Entra ID Roles to Database
* Update user verification logic: when a verified token is received, check if the user exists in the local `users` table. If not, auto-provision them.
* Map Entra ID security groups (e.g., `ClaimGPT-Adjusters`, `ClaimGPT-Patients`) to the local `roles` table (`reviewer`, `submitter`) to restrict access to sensitive routes.

## Task 2: Refactor Database Transaction Management

### [ ] Step 2.1: Remove Premature Commits in `AuditLogger`
* Open [libs/utils/audit.py](file:///c:/Project/ClaimGPT-feature/libs/utils/audit.py#L65).
* Remove the line `self._db.commit()`.
* Replace it with `self._db.flush()`. This inserts the audit log row and generates the database primary key within the current transaction session but delegates the final `commit()` to the parent worker task.

### [ ] Step 2.2: Ensure Session Scope Isolation in Routes
* Audit all FastAPI routers (e.g. `services/ingress/app/main.py`) to verify that sessions generated by `get_db` dependencies are properly closed on exception handling. Ensure no route shares a single session object across different async requests.

## Task 3: Migrate Storage layer to Azure Blob Storage

### [ ] Step 3.1: Write Azure Blob Storage Adapter
* Implement `AzureBlobStorage` in [libs/shared/storage.py](file:///c:/Project/ClaimGPT-feature/libs/shared/storage.py) using the official Azure SDK (`azure-storage-blob`).
* Keep the class interface compatible with the existing `MinioStorage` methods (`upload_file`, `download_file`, `delete_file`, `copy_file`) so that switching from MinIO to Azure Blob Storage is a simple environment variable toggle.

### [ ] Step 3.2: Implement Direct Upload (SAS Token Endpoint)
* Instead of uploading file bytes through the API container, create an endpoint: `GET /claims/upload-token`.
* The endpoint must use Azure SDK's `generate_blob_sas` to create a short-lived (e.g., 15-minute) write-only SAS URL for the specific user's file.
* The frontend React app will fetch this SAS URL and upload the file directly to Azure Blob Storage. This offloads network bandwidth from the API gateway containers.

## Task 4: Integrate Azure Document Intelligence (Serverless OCR)

### [ ] Step 4.1: Create Document Intelligence Client
* In `services/ocr/app/`, implement a new engine connector using `azure-ai-formrecognizer`.
* Add `settings.use_azure_ocr` to configure whether to call the Azure API or run local PaddleOCR.

### [ ] Step 4.2: Implement Digital PDF Bypass (Cost Optimization)
* Verify that before calling the Azure API, the engine checks for digital text using `pdfplumber` (as currently done in `services/ocr/app/engine.py`).
* If `digital_text_len >= 20` and the PDF is extractable, return the extracted text directly and **do not invoke the Azure API**, keeping the OCR cost at $0.00.

## Task 5: Migrate Message Broker to Azure Service Bus

### [ ] Step 5.1: Configure Celery for Service Bus
* In [libs/shared/celery_app.py](file:///c:/Project/ClaimGPT-feature/libs/shared/celery_app.py) (and the environment configurations), swap the broker transport:
  * Install `kombu-azure-service-bus`.
  * Set `broker_url` to `azure-service-bus://:{primary-key}@{namespace}.servicebus.windows.net`.
  * Set `result_backend` to use the Azure Blob Storage backend.
* This ensures that queues are persistent and durable, preventing data loss if Redis restarts.

## Task 6: Enhance Fault Tolerance & Crash Recovery

### [ ] Step 6.1: Celery Soft/Hard Time Limit Exception Handlers
* In `services/shared_tasks.py`, wrap the core loop of each Celery task (`ocr_task`, `parser_task`, `coding_task`, `risk_task`, `validator_task`) in a general `try-except` block.
* Explicitly catch `SoftTimeLimitExceeded` (Celery's timeout signal).
* In the catch block: update `workflow_state` to `FAILED` and write the timeout error message to the database (e.g. in `ocr_jobs` or `parse_jobs`) before exiting, preventing claims from getting stuck in `PROCESSING` status.

### [ ] Step 6.2: Implement a Claim Recovery Daemon
* Create a lightweight cron utility/task (e.g., executing once every 15 minutes) that:
  1. Queries the `claims` table for any records with a status of `PROCESSING` or `STARTING` created more than 30 minutes ago.
  2. Inspects active Celery tasks to see if they are still processing the claim.
  3. If no active task is found, resets the claim status to `FAILED` with an error code ("PIPELINE_TIMEOUT_RECOVERY") and registers the error in the audit log so the user can re-trigger it.

## Task 7: Strengthen HIPAA Data Privacy & Masking

### [ ] Step 7.1: Redact Log Outputs
* Configure Python logging formatters to intercept log messages. Ensure that raw text dumps (such as OCR outputs or SQL variables containing names/emails) are not written to `stdout`/`stderr` where Azure Log Analytics might ingest and store them in plain text.

### [ ] Step 7.2: Implement Database Column Encryption
* For highly sensitive patient fields in the database (such as names, dates of birth, policy numbers, phone numbers, and addresses in `patient_profiles` and `parsed_fields` tables), implement application-level encryption:
  * Use the `cryptography` library (`Fernet` encryption).
  * Store the encryption keys in **Azure Key Vault**, accessed via Managed Identity.
  * Encrypt the fields right before database insertion and decrypt them upon retrieval in the API routes.
